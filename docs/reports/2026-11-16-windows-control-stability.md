## 2. Windows 空闲卡顿：SDK 升级

原环境为 Flutter 3.41.1 / Dart 3.11.0。用户在未控制 Mac 时仍能复现桌面拖拽卡顿，完全退出程序后恢复流畅。

排查中先后尝试输入监听优化、不加载原生输入与剪贴板模块、Release 构建，以及分离 Flutter UI 与 Windows 消息线程，用户均反馈仍然卡顿。软件渲染参数对照也未改善，但该版本 Windows 引擎仍初始化 ANGLE，所以不能用这一项排除图形组件交互。

随后捕获到空闲窗口每 5 秒约 44,000–115,000 条 `WM_NULL` 唤醒，与 Flutter 官方记录的 Windows 计时器溢出问题一致。该问题在 Flutter 3.41.3 修复，本机改用 3.41.4 后重建，空闲 5 秒采样降到约 33–37 条，用户确认恢复流畅。

最终保留的 SDK 相关改动：

- 独立安装 Flutter 3.41.4 / Dart 3.11.1，位置为父目录 `.toolchains/flutter-3.41.4`，没有替换全局 Flutter。
- `pubspec.yaml` 增加 Flutter 最低版本要求 `>=3.41.3`，锁文件与本机 SDK 解析结果同步。
- `tool/check.ps1` 增加 `-FlutterPath` 参数，允许明确指定构建 SDK。
- 撤回未能改善该问题的输入监听重构，以及临时渲染、线程策略和消息计数代码。

这部分卡顿修复来自 SDK / 引擎升级，不应与后续断联日志及原生保护的业务代码改动混为一谈。

详细证据见 [Windows 空闲卡顿排查](../issues/windows-idle-drag-lag.md)。上游依据为 [Flutter #182501](https://github.com/flutter/flutter/issues/182501)、[修复 #182822](https://github.com/flutter/flutter/pull/182822) 与 [3.41.4 更新记录](https://github.com/flutter/flutter/blob/3.41.4/CHANGELOG.md)。

## 3. 控制端断联日志

### 3.1 界面与记录规则

控制端原“模拟桌面”位置改为“断联日志”。`lib/pointer_preview.dart` 保留，并迁移为独立组件测试；控制端不再挂载它，也不再启动用于预览的 Dart Ticker 或逐帧调用原生 `pointer`。鼠标数据转发仍由原有原生采集与发送机制驱动。

每次实际结束控制并收到停止通知时记录一条，正常边缘切回也记录。“返回 Windows”和“TCP 断开”分别呈现，日志中的“连接仍保持”表示当时两端连接尚在。

以下情况不增加返回记录：未成功开始控制、空闲停止通知、同一控制会话的重复停止通知。若紧急停止通知早于原生启动回复到达，也只记录一次，并避免随后又把界面恢复成“控制中”。

### 3.2 字段、筛选与持久化

| 字段 | 含义 |
| --- | --- |
| 时间 | Dart 收到停止通知的时间，界面以本地时间显示到毫秒，持久化使用 UTC |
| 类型、原因与原始代码 | 正常切回、快捷键、连接中断等分类，以及原生上报代码 |
| 控制模式 | 后台边缘控制、窗口内远程控制或本地测试 |
| 持续时间 | 使用 `Stopwatch` 单调计时，避免系统时间调整影响时长 |
| 连接状态 | 停止时是否仍保持连接 |
| 补充信息 | 网络中断状态及新版本原生诊断快照 |

支持按边缘切回、快捷键、连接中断、安全保护、窗口 / 设备、主动停止和其他类型筛选。筛选只影响显示；“清除日志”清除所有类型的历史。

最近 300 条按新到旧自动保存在本机，重启后恢复。使用独立 SharedPreferences 键 `shared_input.control_returns.v1`，写入串行化，防止清除时被尚未完成的旧写入覆盖。日志保存失败不会阻止输入恢复。

Windows 存储文件通常位于 `%APPDATA%\com.example\shared_input\shared_preferences.json`。该文件同时包含应用设置，排查时只读取日志键；日志本身不记录按键内容、连接码、剪贴板或指针轨迹。

## 4. 安全保护误切回：证据与修复过程

### 4.1 旧日志不能直接当作断网证据

首次读取共 14 条：6 条 `edge`、8 条 `hook_lost`，均为后台控制且连接仍保持，部分会话不足 1 秒。重建前备份时增至 19 条：10 条 `edge`、9 条 `hook_lost`。

因此，这次反馈主要是本地输入保护主动结束控制，并非已经证明 TCP 连接中断。同时，旧版本存在原因归类竞争，不能认定每条 `hook_lost` 都代表钩子实际失效。

### 4.2 第一轮：修正时间计算与首次原因归类，实测仍有误退

第一轮修正两类问题：

1. 输入线程先采样 `now`，其他线程随后更新 `lastSeen`，无符号相减可能下溢，把刚发生的活动判断为过期。现对未来时间按新鲜处理，对从未观察到的状态单独处理；Mac 指针反馈超时也显式检查时间先后。
2. 看门狗或快捷键先释放输入，统计消息随后抢先执行 `Stop("hook_lost")`，可能覆盖真正原因。现将会话 `generation`、拦截状态与首次释放原因合并到一个 64 位 atomic，通过 CAS 同时发布原因并解除拦截，后续消息不能覆盖首次原因，旧会话也不能释放新会话。

看门狗和快捷键仍直接在原生层释放输入，不等待 Dart、网络或日志写入。快捷键停止消息增加会话编号校验，主线程停止流程采用已保存的首次原因。

**这一轮没有解决实测现象。** 用户反馈仍误切回，新日志捕获到一例持续 458 ms 的会话：`hook_lost` / `mouse_hook_stale`，而主线程停止快照中鼠标钩子与 Mac 反馈年龄均为 0 ms。

这一证据支持“独立输入消息链路交付先后造成瞬时陈旧”的判断；停止快照晚于触发检查，不能据其还原精确的事件顺序，也不能把所有旧记录归为同一原因。

### 4.3 第二轮：健康检查改为拦截线程响应

最终不再以单个鼠标或键盘回调的间隔作为退出依据，而是检查负责拦截的原生线程是否持续响应：

- 已有 DLL 消息线程使用 50 ms 原生定时器更新心跳，不经过 Flutter、网络或 UI。
- 最近的线程心跳、鼠标回调、键盘回调中任一活动可证明线程正在执行。设备静默本身不再导致切回，连续回调也不会因定时器稍晚被误判。
- 独立看门狗约每 50 ms 检查。线程无响应达到 250 ms 时解除拦截，保存 `hook_thread_timeout` 首次原因。
- 若原生线程在实际停滞后恢复，迟到的定时器不会用一次新心跳掩盖此前已达到的无响应条件。
- 每次开始控制时重新安装钩子，再移除旧句柄；安装失败不进入控制，避免重用此前可能被系统超时移除的钩子。
- 未控制时，钩子继续更新本地观察状态，但不再向主线程转发键盘消息。

正常输入转发没有增加等待、缓存或确认往返。这里检测的是原生线程的响应；它不是 Windows 提供的钩子注册状态查询。[微软文档](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)说明低级钩子超时后可能被静默移除，因此还需要保留独立超时恢复和重新安装机制。

### 4.4 当前保留的保护

| 保护 | 条件 | 行为 |
| --- | --- | --- |
| 拦截线程响应 | 最近有效活动距当前达到 250 ms | 原生解除拦截，恢复 Windows 输入 |
| Mac 指针反馈 | 后台控制时有效反馈中断达到 1000 ms | 原生结束控制并恢复 Windows 输入 |
| Flutter 心跳 | 界面心跳中断达到 3000 ms | 独立看门狗释放输入 |
| 紧急快捷键 | 用户按已设置组合键 | 原生立即解除拦截 |
| 边缘返回 | 满足现有边缘返回策略 | 结束当前控制，通常保留连接 |

本地测试的 30 秒上限、设备移除、窗口模式失焦 / 窗口变化与输入队列溢出等退出路径继续保留。没有通过关闭保护或放宽超时来掩盖问题。

## 5. 新增原生诊断信息

新记录的 `exitDiagnostics` 包括：

- `trigger`：首次释放原因的具体检查，例如 `hook_thread_timeout`、`hook_queue_failed`、`pointer_timeout` 或 `edge`。
- `generation`：原生控制会话编号。
- `mouseAgeMs`、`keyboardAgeMs`：停止时最近键鼠钩子活动的年龄。
- `hookPumpAgeMs`：停止时拦截线程心跳年龄。
- `pointerAgeMs`、`heartbeatAgeMs`：停止时 Mac 反馈与 Flutter 心跳年龄。

`-1` 表示没有观察记录；并发更新造成的未来时间快照按 0 处理。以上年龄是主线程处理停止时的快照，不是最先触发释放的精确时刻。原生会话编号在程序重启后可以重新计数，应结合日志时间判断。

旧记录没有补造诊断字段，也没有清除。尤其不能用旧的 `hook_lost` 记录判断第二轮是否再次误退。

## 6. 验证结果与当前结论

| 验证项 | 结果与范围 |
| --- | --- |
| 静态分析 | 最终代码分析通过 |
| Flutter 完整回归 | 67 项通过，覆盖日志、界面、网络会话及既有功能 |
| 第二轮日志模型检查 | 原生诊断字段扩展后，5 项日志模型测试通过 |
| Windows 原生测试 | 第二轮最终代码下 6 项通过，包含时间边界、线程健康、首次原因、旧会话隔离、并发释放与生产 DLL 接口检查 |
| Windows Debug | 最终版本构建并启动成功，运行错误日志为空 |
| 第二轮日志观察 | 从日志时间 2026-11-16 10:26:58（北京时间）启动后，回看新增 15 条均为 `edge`，未见安全保护触发 |
| 用户实测反馈 | 最新反馈“暂时没有”，暂未再遇到误切回 |

原生测试包括：单个设备静默但线程心跳正常、回调持续但定时器稍晚、并发更新时间晚于调用方时间、真实无响应达到边界、两个线程争抢首次原因，以及旧会话消息不能释放新会话。生产 DLL 接口测试不安装全局钩子，也不合成键鼠输入。

日志与界面回归使用了真实本机 TCP 会话，部分原生停止事件为模拟。用户的双机操作反馈补充了实机证据，但自动测试不等同于长时间实体键鼠测试或真实故障注入。

**当前结论：第二轮修复后短期实测未再复现安全保护误退，继续观察长期表现。第一轮只修时间与归类的版本明确记为未解决。**
