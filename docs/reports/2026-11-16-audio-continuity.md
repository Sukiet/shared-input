# 音频规律性断续修正

基线：2315510。用户已在 Mac 构建并确认音频可回传，但听到规律性小卡顿；更新 Windows 播放端后反馈“基本恢复流畅”。Mac 采集修正尚待更新后验收。

## 排查证据

首版 15 ms 预缓冲没有为正在执行的 WASAPI 写入额外留出余量。Mac 采集回调一次提供一批帧，拆成 5 ms UDP 包后集中到达；Windows 按自己的设备周期读取。包没有丢失，也可能短暂读空并补静音。原逻辑还没有吸收两台机器独立采样时钟偏差的机制。

新增确定性虚拟时间测试：每批 1024 帧、到包延迟 0–8 ms、时钟无偏差、持续 20 秒，旧实现产生 240 帧非预期静音（5 ms），测试失败。新实现同一用例为 0。该复现说明代码存在断音路径，不等同于已测得用户网络或 Mac 的实际采集参数。

Mac 采集回调还存在 `ringLock.try()` 失败便直接丢弃整批 PCM 的路径。消费者复制预分配缓冲时发生短暂竞争，也会丢帧；这类丢帧发生在分包前，没有 UDP 序号缺口，Windows 无法补回。

## 修正

- Windows 按本次设备写入量加所选余量进行预缓冲，避免一次播放写入吃完所有储备。默认 40 ms，控制端音频同步区可设置 10–200 ms，步长 1 ms，松开滑杆后保存并重建音频通道生效。数值越小延迟越低，越大越稳定；此值是播放缓冲余量，不是完整端到端延迟。
- 按平滑后的缓冲深度，通过连续插值与小幅速率校正吸收采样时钟差，最大校正幅度 ±0.3%。不再依赖反复读空或丢弃积压来纠正正常时钟漂移。初次播放与重缓冲增加 5 ms 淡入。
- 默认值下极端积压超过 32 包时才丢弃旧包，保留最近 12 包，限制延迟增长；上限随缓冲设置调整，确保 200 ms 设置也能正常启动。正常时钟偏差测试要求此丢弃路径完全不触发。
- Windows 音频工作线程使用 [MMCSS Audio 任务](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)，并在收包后检查同时到达的播放事件，避免网络事件优先级导致播放饥饿。增加 UDP 系统接收缓冲。
- Mac 采集环形缓冲改为短临界区锁。锁内仅操作预分配内存与复制音频，网络、格式转换和加密仍在锁外；避免正常竞争即丢帧。
- 原生音频状态增加已播放帧数、读空次数、缺包数、积压丢弃数、缓冲深度和速率校正值。它们不改变键鼠协议、音频包格式、音频续租或退出保护。

## 验证与后续

连续性测试覆盖 512 / 1024 / 2048 帧的采集批次、0–8 ms 到包抖动、正负 1000 ppm 的采样时钟偏差、10 / 20 ms 播放写入，以及长达 180 秒的虚拟播放。要求启动后无非预期静音、无读空、无缺包、无积压丢弃，并保持立体声通道关系和有界缓冲。

缓冲设置测试覆盖旧配置默认 40 ms、非法值回退、设置持久化、滑杆操作及角色切换和重启恢复、向原生播放端传值、修改只重建音频通道、重复值不重建，以及 200 ms 缓冲的连续播放。缓冲设置只需更新 Windows 端，可配合现有 Mac 版本使用。

Windows 原生测试还运行静音 PCM 的真实 UDP → 解密 → WASAPI 链路，并要求已播放帧数实际增长。10 项 Windows 原生测试及 Debug 构建通过，已启动新版。未在此 Windows 环境编译 Mac；Mac 本次代码改动也需要拉取构建。

Windows 播放修正可以先配合原 Mac 版本验证；完整修正需要两端更新。两端更新后持续播放音乐、语音，检查规律性停顿、长期漂移与延迟，再测试耳机切换和断网后 Mac 声音恢复。不能将模拟测试通过等同于实际听感已解决。
