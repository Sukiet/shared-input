## 本次范围

在控制端原模拟桌面的位置增加本地历史面板，每个实际结束的控制会话记录一次。保留模拟桌面组件的代码与独立测试，去掉控制端挂载与 Dart 的逐帧 pointer 查询。输入转发与原生采集定时器保持原有实现。

记录包括接收到停止通知的时间、控制持续时间（Stopwatch 单调计时）、控制模式、原因、原生原因、当时的连接状态，以及网络中断时网络层给出的简短状态。收到原生停止通知后才记录；启动失败或重复停止通知不重复计数。正常边缘切回与快捷键退出通常保留连接，不能将其直接当作 TCP 断线。

网络中断与对端结束会话使用不同的本地停止请求标签；原生 stop 通用上报 manual 时，保留该原始代码并补充本地请求原因。若原生层报告其他原因，日志保留原生上报，不擅自改写为网络故障。未知原因仍显示原始代码，归入“其他”。

历史使用独立 SharedPreferences 键 `shared_input.control_returns.v1`，按新到旧保存最近 300 条。按类型筛选只影响显示；清除会删除所有类型的记录并覆盖磁盘存储。写入串行化，避免在旧写入尚未完成时清除后又恢复旧内容。日志保存失败不会阻止输入恢复。

## 日志首版的限制（历史）

日志首版没有修改原生输入与看门狗逻辑；后续修复见下方。所有保护阈值保持原值。

首版原生层可能先释放输入，再由统计消息抢先归类为 hook_lost，掩盖原始 pointer_timeout、heartbeat 或 shortcut。因此旧日志中的原因不能直接认定为真实故障来源；首次原因保留已在后续修复，旧记录保持原样。日志时间是 Dart 收到停止通知的时间，不是原生线程最先释放输入的准确时间；若主线程阻塞，两者可能有延迟。

相关竞态与测试随后在下文修复阶段处理。自动测试未覆盖跨机器实体故障注入，用户双机操作反馈见最终状态。

## 2026-11-16：安全保护误退修复

用户反馈安全保护频繁切回。首次读取 14 条历史：6 条 edge、8 条 hook_lost，全部为后台控制、连接仍保持；部分会话不足 1 秒。重建前备份时历史增长至 19 条（10 条 edge、9 条 hook_lost）。这些是旧版本上报，受首版归类竞态影响，不能证明每次都是钩子实际失效。

代码修复：

- 钩子时间戳为 0 时仍视为未观察；lastSeen 晚于调用方采样的 now 时视为新鲜，避免无符号下溢误判。真实达到 250 ms 仍拒绝。
- 指针反馈时间先读取，再采样 now，并显式检查 now >= received；达到 1000 ms 仍恢复本机输入。
- DLL 将 generation、输入拦截状态与首次释放原因合并到一个 64 位 atomic。释放时通过 CAS 同时发布原因并解除拦截；旧 generation 不能释放新会话。看门狗和快捷键不等待 Dart 或主线程处理日志。
- 主线程 Stop 采用原子保存的首次原因。统计定时器、延后的看门狗或快捷键消息不能覆盖它；快捷键停止消息同时校验 generation。
- 区分鼠标钩子过期、键盘钩子过期、拦截状态丢失及键盘消息投递失败。未控制时钩子只更新本地观察状态，不再向主线程转发键盘消息。

新日志增加 exitDiagnostics：触发检查、generation，以及停止时鼠标钩子、键盘钩子、Mac 反馈与界面心跳的年龄。-1 表示没有观察记录，未来时间快照按 0 处理。年龄是主线程处理停止时的快照，可能晚于最初释放时刻，不是触发瞬间采样。

验证：原生时间边界、并发更新、首次原因保留、旧消息隔离及并发释放测试通过，且不安装钩子、不注入输入地检查生产 DLL 导出；6 项原生测试、67 项 Flutter 测试与静态分析通过。第一轮 Windows Debug 重建后用户反馈仍误退，不能标记为解决，见下文第二轮。Mac 无需为本次 Windows 改动更新。

### 第二轮：不再把设备回调静默当作钩子失效

第一轮修复后用户仍报告误退。新版抓到 generation=7、持续 458 ms 的 hook_lost，trigger=mouse_hook_stale，但主线程停止快照中鼠标钩子与 Mac 反馈年龄均为 0 ms。这支持“独立消息链路交付先后导致瞬间陈旧”的判断，单修无符号下溢不足以解决实际现象，不能把第一轮标记为解决。

第二轮把健康判据改为原生拦截线程的响应：

- 已有 DLL 消息线程使用 50 ms 原生定时器更新心跳，不经过 Flutter、网络或 UI。
- 心跳或实际键鼠回调中任一最近活动可证明线程正在执行，避免只用单个设备的回调间隔判断失效。未来时间仍按新鲜处理。
- 独立看门狗每约 50 ms 检查；线程无响应达到 250 ms 时直接解除拦截，并保存 hook_thread_timeout 首次原因。恢复较晚的原生定时器也会保留超时结果，不用迟到心跳掩盖已发生的无响应。
- 每次开始控制时重新安装有效钩子，再移除旧句柄，避免重用以前可能被 Windows 超时移除的钩子。安装失败不进入控制。
- Mac 反馈 1 秒、Flutter 心跳 3 秒与紧急快捷键保持原有行为。正常输入转发不等待验证、不增加缓存或延时。
- 日志增加 hookPumpAgeMs，显示“拦截线程心跳”年龄。鼠标/键盘回调年龄继续作为观察信息，单独陈旧不再是退出条件。

这证明的是拦截线程的响应，不是 Windows 提供的钩子注册状态查询。Windows 文档指出低级钩子在超时后可能被静默移除且没有查询通知，因此同时保留独立线程超时释放，并在下一次控制开始时更新句柄。

第二轮验证：静默设备但线程心跳正常不退出、回调持续但定时器滞后仍健康、真实线程停滞达到边界退出、首次原因和跨会话隔离等原生测试通过。随后用户反馈“暂时没有”再误切回；当前记为短期实测正常，仍需长期观察。

参考：[Microsoft LowLevelMouseProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)、[Raw Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input)。

第二轮启动于日志时间 2026-11-16 02:26:58Z；首次回看新增 2 条均为 edge，连接保持，持续时间约 4.2 秒和 23.2 秒，拦截线程心跳年龄分别为 47 ms 和 31 ms。此短样本未见安全保护误退，尚不能替代用户确认或长期稳定性测试；原历史未清除。

第二轮后续回看累计 15 条新记录，均为 edge，未出现 hook_lost 或其他安全保护原因；该次回看时用户尚未明确确认；随后用户反馈“暂时没有”，现同时保留日志观察与用户反馈。静态分析再次通过，程序错误日志为空。
